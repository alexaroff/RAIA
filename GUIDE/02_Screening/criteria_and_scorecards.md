# Критерии и Scorecards

**Критерии скрининга** — это заранее определённый и согласованный с нанимающим менеджером набор требований, по которым принимается решение «двигаемся дальше / не двигаемся».

**Scorecard** — инструмент, который фиксирует эти критерии, делает оценку более объективной и позволяет сравнивать кандидатов между собой.

Без чётких критериев скрининг превращается в набор субъективных впечатлений. С хорошим scorecard он становится воспроизводимым процессом.

---

## Зачем это нужно

1. **Снижение bias**  
   Когда критерии зафиксированы до начала просмотра резюме, меньше влияния первого впечатления, названия компании или «похожести» кандидата на текущую команду.

2. **Калибровка с Hiring Manager**  
   Большинство конфликтов «рекрутер привёл не тех» возникают из-за того, что стороны по-разному понимали must-have.

3. **Скорость и последовательность**  
   Решения принимаются быстрее и по одним и тем же правилам, даже если скринят разные люди.

4. **Возможность улучшать процесс**  
   Если решения фиксируются, можно анализировать: какие критерии реально предсказывают успешное прохождение следующих этапов.

> Scorecard на этапе скрининга должен быть проще, чем на полноценном интервью. Его задача — быстро и надёжно отсечь тех, кто точно не подходит, а не провести глубокую оценку.

---

## Must-have, Nice-to-have и Deal-breakers

Правильное разделение требований — основа качественного скрининга.

| Тип | Определение | Как использовать на скрининге |
|-----|-------------|-------------------------------|
| **Must-have** | Без этого кандидат не может выполнять работу на нужном уровне | Жёсткий фильтр. Отсутствие = reject (или очень сильное обоснование исключения) |
| **Nice-to-have** | Значительно повышает вероятность успеха, но не является обязательным | Учитывается при сравнении кандидатов, прошедших must-have |
| **Deal-breaker** | Жёсткое ограничение, которое делает найм невозможным или крайне рискованным | Немедленный reject (пример: отсутствие права на работу, принципиальное несовпадение по формату работы, критичный conflict of interest) |

### Как правильно определять Must-have

Хороший must-have отвечает на вопрос:  
«Если у человека этого не будет — он с высокой вероятностью провалится в первые 3–6 месяцев или создаст неприемлемый риск?»

Примеры сильных must-have:
- Коммерческий опыт разработки на конкретном стеке (для middle+/senior инженера)
- Опыт управления командой от N человек (для Team Lead)
- Право на работу в нужной юрисдикции
- Готовность к определённому формату (офис / гибрид / релокация)

Примеры слабых «must-have» (которые часто оказываются nice-to-have):
- «Опыт именно в нашей индустрии»
- «Работал в FAANG / крупной известной компании»
- «Закончил топовый вуз»
- «Ровно 5+ лет опыта»

## Как построить рабочий Scorecard для скрининга

### Шаг 1. Согласовать с Hiring Manager

До начала поиска зафиксируйте:
- 3–6 must-have критериев
- 3–5 nice-to-have
- Жёсткие deal-breakers (если есть)
- Примерный уровень (junior / middle / senior / staff)

Лучший формат — короткая письменная фиксация после intake-встречи.

### Шаг 2. Сделать критерии наблюдаемыми

Плохо: «Хорошие коммуникативные навыки»  
Лучше: «Способен чётко объяснить сложную техническую тему за 2–3 минуты без воды»

Плохо: «Опыт работы с высоконагруженными системами»  
Лучше: «Есть опыт систем с нагрузкой от X RPS / пользователей / данных» (если это действительно критично)

### Шаг 3. Определить шкалу оценки

Для скрининга обычно достаточно простой шкалы:

| Оценка | Значение |
|--------|----------|
| 1 | Не соответствует / отсутствует |
| 2 | Частично соответствует / есть сомнения |
| 3 | Соответствует ожиданиям |
| 4 | Превышает ожидания |

Или ещё проще для раннего этапа: **Pass / Borderline / Reject**.

### Шаг 4. Решить, как считать итог

Варианты:
- **Жёсткий фильтр**: любой must-have = 1 → Reject
- **Взвешенный**: must-have имеют больший вес
- **Пороговый**: нужно набрать минимум N баллов по must-have + overall impression

На этапе скрининга чаще всего работает самый простой вариант — жёсткий фильтр по must-have + качественная оценка остальных факторов.

## Пример структуры Scorecard (скрининг)

**Позиция:** Backend Engineer (Middle+/Senior)

**Must-have**
- [ ] Коммерческий опыт на Go или Java (от 2 лет)
- [ ] Опыт проектирования и поддержки сервисов в production
- [ ] Понимание баз данных (SQL + хотя бы одна NoSQL)
- [ ] Готовность к гибридному формату (офис 2–3 дня)

**Nice-to-have**
- Опыт с Kubernetes / service mesh
- Опыт менторства или проведения code review
- Вклад в open-source

**Deal-breakers**
- Нет права на работу в РФ / нужной стране
- Принципиальное нежелание рассматривать гибрид

**Итоговое решение**
- Pass / Borderline / Reject
- Краткое обоснование (1–3 предложения)
- Что обязательно уточнить на звонке

## Калибровка с Hiring Manager

Scorecard бесполезен, если рекрутер и менеджер понимают критерии по-разному.

Практики, которые работают:

1. **Совместный разбор 5–7 резюме** в начале поиска  
   «Этих я бы пропустил / отклонил по таким причинам. Согласны?»

2. **Регулярный feedback loop**  
   После первых 3–5 интервью сверяйтесь: кто из прошедших скрининг оказался сильным/слабым и почему.

3. **Пересмотр критериев**  
   Если рынок не даёт людей с изначальными must-have — критерии нужно осознанно менять, а не «тихо смягчать».

---

## Типичные ошибки

- Делать 12–15 «must-have» — это уже не must-have.
- Писать критерии размыто («хороший опыт», «сильные навыки»).
- Не согласовывать scorecard с менеджером до начала скрининга.
- Менять критерии в процессе без фиксации («ну этот вроде тоже подойдёт»).
- Использовать один и тот же scorecard на все роли без адаптации.
- Оценивать nice-to-have так же строго, как must-have.
- Не фиксировать обоснование решения — потом невозможно анализировать качество фильтра.

---

## Практический чек-лист

- [ ] Must-have, nice-to-have и deal-breakers согласованы письменно
- [ ] Критериев must-have не больше 5–6
- [ ] Каждый критерий сформулирован наблюдаемо
- [ ] Есть простая шкала оценки
- [ ] Рекрутер и Hiring Manager провели хотя бы одну калибровочную сессию
- [ ] Решение по каждому кандидату фиксируется с кратким обоснованием
- [ ] После первых интервью критерии пересматриваются при необходимости
